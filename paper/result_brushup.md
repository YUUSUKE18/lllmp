## 結論

- ローカル LLM が生成するコードには、**機能テストは通るが敵対的入力で可用性が失われる
  「セキュリティギャップ」**が、温度・プロンプト形式（zero/one/few-shot）に依らず一貫して存在する。
  - 例: cwe400_pair_sum（CWE-400）の java では gemma4:e2b の func は 102/120 だが、
    敵対的入力（40 万要素）を処理できた世代は 0。
    **ただしこのギャップは thinking を有効にすると消える**（同タスク go/java 計 40 世代で
    func-sec 0/40 → 39/40）。ギャップは「モデルの限界」ではなく推論設定に強く依存する。
  - 温度を変えてもギャップは消えない。gemma4:e2b は温度 0.1→1.0 で func 67.5%→61.9%、
    func-sec 39.9%→37.5% とほぼ不変。qwen3.5:4b は func も安全な世代数も両方減る
    （38.2%→24.3%、26.1%→19.9%）。
- **ギャップの大きさはモデルとタスクの組で決まり、機能性能が高いモデルほど安全とは限らない。**
  - **thinking を無効にした条件**では、8 タスク合計で gemma4:e2b が全言語で qwen3.5:4b を
    上回る（func-sec: go 183 対 79、ts 424 対 183、java 536 対 450、各 960 世代）。
    全スイープは応答欠落を避けるため `think=false` で取得しており、この順位はその設定下の値である。
  - **モデル順位は推論設定を揃えれば入れ替わらない。** 両モデルを同一 **30 条件
    （8 タスク × go/ts/java × zero-shot、各 300 世代）**で比べると、func-sec は
    **think OFF どうしで gemma 108 対 qwen 67（p=3.1×10⁻⁴）、think ON どうしで
    gemma 180 対 qwen 102（p=2.4×10⁻¹⁰）**。**どちらの設定でも gemma が有意に上**である。
    （go/java の 18 条件だけで見たときは ON で 109 対 90・p=0.056 と有意でなかったが、
    ts を含めると差が開く。qwen の ts が thinking で崩れるため。）
  - **推論設定の効果とモデル間の差は同じ桁で、どちらが大きいかは切り口で変わる。**
    同一モデル内の think 有無の差は gemma4:e2b が 36%→60%（+24 ポイント、p=5.6×10⁻⁹）、
    qwen3.5:4b が 22%→34%（+12 ポイント、p=0.002）。
    同一設定でのモデル間の差は **think OFF で 14 ポイント、think ON で 26 ポイント**。
    つまり **think ON でのモデル間差（26）は gemma の think 効果（24）を上回り、
    qwen の think 効果（12）の 2 倍以上**である。
    **「モデル選択より推論設定のほうが効く」とは言えない。どちらも同程度に効くので、
    比較では両方を固定する必要がある。**
  - **「書き方の癖」もモデル固有ではなく推論設定で切り替わる。** cwe400_pair_sum で
    gemma4:e2b は think OFF なら **20/20 が二重ループ**、think ON なら **20/20 がハッシュ表**を書く。
    func は 39/40 のまま変わらず func-sec だけが 0/40 → 39/40 に跳ねる。
    thinking 無効時に qwen3.5:4b が java で 64 対 0 と逆転していたのは、
    qwen が既定でハッシュ表を選ぶためで、系列や規模では説明できない
    （同じ Qwen 系列の qwen2.5-coder:1.5b は 80/120 が二重ループ）。
  - **Go は thinking 無効時にはどのモデルでも最も弱い言語**だが、**thinking を有効にすると
    最弱言語が入れ替わることがある**。thinking 無効時の func は gemma4:e2b 448/960、
    qwen3.5:4b 125/960、Bonsai は 8B/4B とも 0。同一条件で thinking を有効にすると
    func-sec は qwen が go 0/100 → 37/100、gemma が go 14/100 → 58/100 に上がり、
    **go と java の差はほぼ埋まる**（gemma think ON で go 58/100 対 java 65/100）。
    **ただし qwen の think ON では ts が go を下回って最弱になる**（ts 4/100 対 go 37/100）。
    言語の難易度順序は think OFF では 3 モデル共通（go < ts < java）だが、
    **推論設定をまたぐと共通でない**（qwen think ON は ts < go < java）。
- **1-bit 圧縮モデル（Bonsai 8B/4B）は、通常量子化の 4B 級（qwen3.5:4b）に機能でも安全性でも届かない。**
  - func は 7 タスクすべてで最低（14〜25%、qwen3.5:4b の半分以下）。4B に落とすと 0〜0.6%。
  - func が通った世代に限っても脆弱率は 0.36〜0.59 で、gemma4:e2b（0.00〜0.07）・
    qwen3.5:4b（0.01〜0.15）より有意に高い（Fisher、Holm 補正後 8 比較すべて p<10⁻⁴）。
  - 常駐メモリは小さいが生成速度は 1.5B モデルより遅く、「圧縮でコストを下げる」路線は成立しない。
- **推論設定（thinking）の効果は、全体平均で語ると実態を取り違える。**
  両モデルを 3 言語 30 条件 300 世代で揃えると func-sec は
  gemma4:e2b が 36%→60%（p=5.6×10⁻⁹）、qwen3.5:4b が 22%→34%（p=0.002）。
  内訳は次のとおり偏っており、**偏りの形は 2 モデルで共通する**。
  - **増分の大半が cwe400_pair_sum 1 タスク由来**（gemma は 0/60 → 56/60 で増分の 78%、
    qwen は 6/60 → 28/60 で 63%）。**このタスクを除くと両モデルとも改善が有意でなくなる**
    （gemma 108/240 → 124/240、p=0.17／qwen 61/240 → 74/240、p=0.22）。
    thinking が効くのは「**計算量の選択がそのまま安全性になる**」タスクであり、
    そこでは think OFF が 20/20 二重ループ、think ON が 20/20 ハッシュ表と実装が入れ替わる。
  - **言語で効果が正反対になり、ts では悪化する。** go は func-sec が
    gemma 14/100→58/100（p=8.4×10⁻¹¹）・qwen 0/100→37/100（p=2.4×10⁻¹³）、
    java は gemma 36/100→65/100（p=6.8×10⁻⁵）・qwen 39/100→61/100（p=0.0029）と改善するのに、
    **ts は gemma が 58/100→57/100 で全く変わらず**（func は 88/100→68/100 に低下）、
    **qwen は 28/100→4/100 と有意に悪化する**（p=3.7×10⁻⁶。func も 32/100→5/100）。
    cwe400_pair_sum を除いた gemma の ts は **有意に悪化**する（58/80→40/80、p=0.0056）。
    **thinking を有効にしたとき ts は両モデルで最も割に合わない言語**であり、
    qwen では最弱言語が go から ts に入れ替わる。
  - ただし thinking が上げるのは「仕様を正しく満たす」能力だけで、**仕様に書かれていない
    資源制約は考慮しない**。**cwe770_stream_max は gemma では 3 言語 30 世代すべてで
    func-sec 0 のまま**で、func がむしろ 30/30→20/30 に落ちる。
    qwen も go と ts では 0/10 のままだが、**java だけは 7/10 が合格する**（0/30→7/30、p=0.011）。
    合格する 7 世代は `Scanner` でトークン単位に読み進めており、
    **同じタスク・同じ設定でも言語の既定イディオムが結果を決める**。
    qwen の cwe401_memo_retain は func 17/60→32/60 と上がりながら func-sec 12/60→1/60 に落ちる
    （gemma は go/java だけなら 4/40→11/40 と改善するが、ts を含めると 18/60→19/60 で消える）。
  - **thinking は資源制約に配慮しようとするが、そのための API を正しく使えない。**
    **4 通りの壊れ方**がモデル × 言語ごとに別々の形で出る:
    qwen(go) は `io.ReadAll`+`strings.Split` で RSS 125〜248MB に達して落ち、
    gemma(go) は `bufio.Scanner` に `Buffer()` を設定せず既定 64KB 上限で
    `Scan()` が false になり **黙って `count=0` を出力**、
    gemma(ts) は逐次読み込みのつもりで `process.stdin.readSync` を呼び、
    **その型に存在しないメソッドなので型エラーでコンパイルが通らない**
    （22/100 世代が `readSync` を使い、うち 19 世代が `error TS2339` で落ちる）、
    **qwen(ts) は非ブロッキングの `process.stdin.read()` に乗り換える**
    （think OFF では 63/100 が `readFileSync(0)` だったのが ON では 77/100 がこちら）。
    `read()` はバッファが空なら `null` を返すので、`null` ガードを
    **トップレベルの `return` で書いて `TS1108` でビルド不成立になるか**（31/100）、
    **入力を読まないまま `count=0` を出力する**（21/100）。
    **think OFF では `TS1108` は 0/100 件**なので、これは thinking が持ち込んだ失敗である。
    可用性テストでは「落ちる」「誤答」「ビルド不成立」と別々に現れ、誤答がいちばん検知しにくい。
  - **thinking は既定イディオムを入れ替える。入れ替え先が安全なら跳ね上がり、
    壊れた API なら全滅する。** cwe400_pair_sum（二重ループ → ハッシュ表、0/40→39/40）と
    ts の標準入力（`readFileSync(0)` → `process.stdin.read()`、28/100→4/100）は
    同じ機構の両方向の現れである。**どちらに転ぶかは事前に予測できない。**
  - 安全側に出る要因が**言語ごとの既定イディオム**であることも確認できた。同一モデル・
    同一プロンプト・thinking 有効で、cwe770_stream_max の go は 10/10 が
    `io.ReadAll`+`strings.Split` で入力を丸ごとバッファして全滅する一方、
    java は 8/10 が `Scanner` でトークン単位に読み 7/10 が安全に通る。
  - **コスト増の倍率はモデルによらず 5〜9 倍**（gemma4:e2b は 1 世代 9.5 秒 → 51.6 秒で 5.5 倍、
    qwen3.5:4b は 約 95 秒 → 約 12〜14 分で 8〜9 倍）。ただし**絶対値は一桁違い**、
    180 世代の取得は gemma が 4 時間、qwen が約 36 時間。
    同一プロンプトでの thinking 出力長が 1,441 字 対 13,630 字と約 9 倍違うことが効いている。
    **コストは言語に依らずほぼ一定**（qwen の ts 100 世代は連続 20 時間 2 分＝1 世代 12.0 分）
    なので、**ts では費用対効果だけが崩れる**（20 時間を費やして func-sec 4/100）。
- したがってローカル LLM でコードを生成する場合、機能テストとは別に
  **敵対的入力に対する可用性の動的テストを、モデル×タスク×推論設定の単位で行う**必要がある。
  モデルの一般的な性能順位や系列からは安全性を推定できず、
  **推論設定を揃えない比較は順位を誤らせる**。
  さらに **thinking を有効にすれば安全になるという期待は成り立たない**。
  効くのは計算量の選択が安全性に直結するタスクに限られ、言語によっては
  （とくに ts では）機能性ごと落とす。**推論設定は「上げる／下げる」ではなく
  「生成される定石を入れ替えるもの」として扱い、入れ替え後を必ず測り直す必要がある。**

## 元の結論からの変更点

| 元の記述 | 変更 | 理由 |
|---|---|---|
| 可用性と脆弱性というセキュリティのトレードオフ | 機能性と可用性の「ギャップ」 | 本検証の脆弱性は可用性の喪失そのもので、2 軸は func（機能）と sec（可用性）。データが示すのは片方を上げると片方が下がる関係ではなく、func が通っても sec が通らない現象 |
| Temperature を変更した際に特に生じていた | 温度に依らず一貫して存在 | 8 タスク共通データで gemma4:e2b は温度で不変、qwen3.5:4b は func と安全な世代数が同時に減る。温度で強まる証拠はない |
| 1-bit 8B 級は通常量子化 4B 級と同等にならない | 維持し、根拠を追加 | 4B でも回復しないこと、func 通過時の脆弱率が有意に高いことを追記 |
| Go は gemma4 優位、Java/TS は qwen3.5:4b 優位 | 全言語で gemma4 優位、Go は全モデルで最弱、逆転はタスク×モデル固有 | 8 タスク合計の func-sec で gemma4 が 3 言語すべて上。qwen3.5 が上回るのは 24 セル中 4 セルのみ |
| 学習データの差による可能性 | モデル個体の癖として記述 | 同系列の qwen3.5:4b と qwen2.5-coder:1.5b で安全な定石の有無が異なる |

## thinking 反映による変更点（2026-09-21）

## gemma 側 thinking 取得による訂正（2026-09-22）

09-21 の更新では qwen3.5:4b だけ thinking を有効にして gemma4:e2b（thinking 無効）と比べ、
「順位は推論設定で反転する」と書いた。**これは片側だけ設定を変えた比較で、誤りだった。**
gemma4:e2b を同一 18 条件で取得して訂正する。

| 更新前（09-21） | 更新後（09-22） | 理由 |
|---|---|---|
| **順位は推論設定で反転する**（think ON の qwen 90/180 が think OFF の gemma 40/180 を上回る、p=5.8×10⁻⁸） | **反転しない**。設定を揃えると think OFF どうしは 40 対 38（p=0.90）、think ON どうしは gemma 109 対 qwen 90（p=0.056） | gemma も thinking で 22%→61% に上がるため、片側だけ有効にした比較が反転を作っていた |
| gemma4:e2b の think 有効時は未取得、優劣は未決着 | 取得済み（180 世代、docker_err 0・空応答 0）。**gemma が僅かに上だが有意でない** | 同一 18 条件・同一 `num_ctx` で実測 |
| （記述なし） | **推論設定の効果はモデル間の差より大きい**を追加 | モデル内の think 差は 22→61 / 21→50 ポイント、同一設定のモデル間差は 0〜11 ポイント |

## 3 言語への拡張による訂正（2026-09-24）

09-22 時点の gemma4:e2b は go/java 18 条件のみだった。ts 9 条件と cwe400_unique 3 条件を

効くのは計算量の選択が安全性に直結するタスクに限られ、言語によっては逆効果になる。

## qwen 側 3 言語への拡張による訂正（2026-09-26）

09-24 時点で gemma4:e2b は 30 条件（3 言語）、qwen3.5:4b は 18 条件（go/java のみ）だった。
qwen に **ts 9 条件と cwe400_unique 3 条件**を追加して **30 条件 300 世代**にし、
**両モデルの条件集合を完全に一致**させた。これで初めて 300 世代同士の直接比較が成立する。

| 更新前（09-24 まで） | 更新後（09-26） | 理由 |
|---|---|---|
| **推論設定の効果はモデル間の差より大きい**（モデル内 22→61 / 21→50 ポイント 対 モデル間 0〜11 ポイント） | **撤回。同じ桁で、切り口次第で逆転する。** モデル内の think 効果は gemma +24・qwen +12 ポイント、モデル間差は think OFF 14・**think ON 26 ポイント**。think ON のモデル間差が gemma の think 効果を上回る | 旧値のモデル間差は go/java 18 条件のもの。ts を含めると qwen だけが崩れるので差が開く |
| 「**どのモデルを選ぶかより、どの推論設定で動かすかのほうが安全性を左右する**」 | **撤回。どちらも同程度に効く**ので、比較では両方を固定する | 上と同じ |
| モデル間の優劣は僅差で有意でない（think ON で gemma 109 対 qwen 90、p=0.056） | **どちらの設定でも gemma が有意に上**（OFF 108/300 対 67/300、p=3.1×10⁻⁴／ON 180/300 対 102/300、p=2.4×10⁻¹⁰） | 条件集合が一致したので 300 世代で検定できる |
| **Go はどのモデル・どの設定でも最も弱い言語** | **thinking 無効時のみ。qwen の think ON では ts が最弱**（func-sec 4/100 対 go 37/100）。順序は think OFF の go<ts<java から ON の ts<go<java へ入れ替わる | qwen の ts 100 世代を取得した |
| qwen の thinking 効果は func 23%→73%、func-sec 21%→50%（p=1.4×10⁻⁸） | **func 25%→48%、func-sec 22%→34%**（p=0.002）。旧値は go/java に限れば正しい（39/200→98/200、p=6.3×10⁻¹⁰） | ts が両方を下げる |
| thinking の効果が言語で正反対になるのは gemma の所見（go/java 改善・ts 不変） | **両モデル共通**。ただし **qwen の ts は「不変」ではなく有意に悪化**（28/100→4/100、p=3.7×10⁻⁶） | 同上 |
| **cwe770_stream_max は両モデルとも func-sec 0 のまま** | **訂正。qwen の java は 7/10 が合格**（0/30→7/30、p=0.011）。0 のままなのは gemma の 3 言語と qwen の go/ts | 09-21 の「cwe770_stream_max(go) は 0 のまま」を 09-22 に言語の限定なしで一般化したのが誤りだった |
| 壊れ方は 3 種（qwen(go) メモリ枯渇・gemma(go) 誤答・gemma(ts) TS2339） | **4 種**。qwen(ts) は非ブロッキングの `process.stdin.read()` に乗り換え、`TS1108`（31/100）と黙った `count=0`（21/100）の 2 症状を出す | 生成コード 100 世代の静的集計 |
| 増分が 1 タスクに偏るのは gemma の所見（78%） | **両モデル共通**（gemma 78%・qwen 63%）。**除くと両方とも有意でなくなる**（p=0.17／p=0.22） | qwen も 30 条件になった |
| 空応答は qwen 16/180 | **26/300**（go 8・ts 10・java 8）。3 言語にほぼ均等で、**ts の崩壊は空応答では説明できない**（10 件全部除いても func-sec 4/90） | 同上 |

**この拡張で最も重要な含意**: thinking は安全性を「上げる／下げる」ものではなく、
**生成される定石（既定イディオム）を入れ替えるもの**である。入れ替え先が安全なら
func-sec は跳ね上がり（cwe400_pair_sum: 二重ループ → ハッシュ表、0/40→39/40）、
壊れた API なら機能性ごと全滅する（qwen の ts: `readFileSync(0)` → `process.stdin.read()`、
28/100→4/100）。**どちらに転ぶかは事前に予測できず、モデル × 言語 × タスクごとに測るしかない。**
