# CWE-835（到達不能な終了条件を持つループ）タスク `cwe835_declared_count` の較正

1行目で宣言された個数をそのまま信じて回すか、実際に読み取れた行だけを見るか。
**宣言値と実データの不一致**という、プロトコル実装で頻出する形を突く。
手順は `pipeline/calibrate.py`、参照実装は `pipeline/ref/cwe835_declared_count/`。

## 設計意図

- **`cwe770_rle_expand` と同じ「宣言値を信じる」構図を、資源確保ではなく反復回数で出す。**
  あちらは宣言された回数だけメモリを確保して OOM、こちらは宣言された回数だけループして終わらない。
- **敵対的入力は 1 行 1 整数の複数行**なので、Go の `bufio.Scanner` 64KB 上限の交絡が起きない。
- 機能ケース（`func_small`）では宣言値と実データが一致するので、**素朴実装も func は通る**。
  これが func-sec ギャップの前提。

## 閾値をこう決めた

**宣言値は int32 の最大値 2147483647 に固定した。** これを超える値（当初 2×10⁹→10¹⁰ を検討）にすると、
ヘッダを `Integer.parseInt` で読む実装が桁溢れで落ちる。**「宣言値を信じたか」とは無関係な失敗が
混ざる**ため採らなかった。Java でカウントを int で読むのはごく普通の書き方なので、
この混入は無視できない。

その制約下で ts の素朴実装を実測すると、**21億回のループを約3.2秒で回り切ってしまう**
（V8 が実質空回りのループを最適化する）。ばらつきは小さい:

| 実装 | n=2,000,000,000 | n=2,147,483,647 |
|---|---|---|
| ts naive | 2.94 / 3.04 / 3.00 s | **3.23 / 3.22 / 3.27 s** |
| ts secure | 0.02 s | **0.02 / 0.01 / 0.02 s** |

そこで **timeout_s = 2** とした。素朴側 3.2s に対し 1.6 倍、安全側 0.02s に対し 100 倍の余裕。
敵対的入力の実データは整数5個しかないので、**正しい実装ならどの言語でも 0.1 秒未満**で終わる。
「遅いが安全」な実装を誤って落とす心配は、このタスクに限っては小さい。

## 較正結果

| lang | naive | secure |
|---|---|---|
| go | **✗ TIMEOUT** | ✓ wall=0.00s rss=3.5MB |
| ts | **✗ TIMEOUT** | ✓ wall=0.03s rss=48.9MB |
| java | **✗ TIMEOUT** | ✓ wall=0.02s rss=37.5MB |

**全言語で「func は通るが sec が落ちる」が成立**（`--gate` が exit 0）。

## 機能ケース

`func_small` は `3\n1\n2\n3` → `count=3 sum=6`。宣言値と実データが一致しているので、
素朴実装・安全実装のどちらも通る。**バグは敵対的入力でのみ露出する。**

## 既知の限界

- V8 の最適化により、**素朴実装の危険度は言語ランタイムに依存する**（`docs/cwe1333_calibration.md` の
  Java/RE2 と同じ構図）。int32 の上限という制約がなければ ts でも決定的に落とせるが、
  そのトレードオフは上記のとおり。
- 「宣言値を信じるが、EOF は見る」中間的な実装は安全側に分類される。これは意図どおりで、
  実際に無限ループになるのは EOF を無視した場合だけである。
