# int32 混入があった旧 CWE-401 データ（2026-08-27 退避）

`cwe401_memo_retain` の初回スイープ36条件360世代。**機能ケースが小さすぎたため、
軌道の中間値が int32 を超える点を機能テストで検出できず**、型の選択ミスによる失敗が
「保持しすぎ（CWE-401）」の失敗と混ざっていた。

## 何が混ざっていたか

敵対的入力（開始 10^9）の軌道は最大 4.7×10^14 に達する。これを `int` で持つ実装は桁溢れして
負値に回り込み、1 に到達せず無限ループ（TIMEOUT）やクラッシュになる。
**狙っていた「中間値を全部メモ化してメモリを食い潰す」とは別の欠陥である。**

世代単位のギャップ（func 通過 & sec 失敗）65件の内訳:

| lang | ギャップ世代 | 機序 |
|---|---|---|
| ts | 17 | 12件が経路保持（狙いどおり） |
| go | 4 | 2件が rss 超過（狙いどおり） |
| java | 42 | **40件が int32 桁溢れ（別要因）** |

java は `Map<Integer, Long>` や `steps(int n)` を書いた世代がほとんどで、
`ok` は 120世代中 5件しかなく、**言語間比較には使えない**。

## 修正

- 機能ケースに軌道が int32 を超えるクエリ `1000000001`（最大中間値 4.05×10^9）を追加。
  → int で持つ実装は **func で落ちる**ので、ギャップ世代から自動的に除外される。
- 仕様にも「途中に現れる値は 32bit 整数には収まりませんが、64bit 整数の範囲には収まります」と明記。

修正後のデータは `reports/` 直下にある。**本ディレクトリのデータとは func の定義が違うため直接比較できない。**

## 副産物

「64bit を要求する仕様で java は int を選びがち」という傾向自体は独立した知見であり、
CWE-190（整数オーバーフロー）のタスク候補になる。ここのデータはその証拠として使える。
