## 結論

**「素朴＝危険」はモデル固有ではなく、モデル×言語で決まる。**
gemma4:e2b が全360世代で二重ループを選んだのに対し、qwen3.5:4b は **Java でだけハッシュ表を既定にする**。

- 全体で func 127/360、sec 67/360、func-sec 65/360。
- **セキュリティギャップ（func 通過 & sec 失敗）は62世代**。**62件すべて TIMEOUT** で、
  誤答・メモリ超過は1件も含まれない。純粋に O(n²) を書いた結果である。
- 条件単位でギャップ = 1.000 は **36条件中12条件**（ts 9 / go 3 / **java 0**）。

## 言語で結論が割れる

ビルドが通った世代だけを分母にすると、敵対的入力での挙動は言語ごとに別物になる:

| lang | ビルド成功 | ok（安全） | TIMEOUT | wrong_answer | crash |
|---|---|---|---|---|---|
| go | 19/120 | **0** | 15 | 3 | 1 |
| ts | 77/120 | **1** | 60 | 14 | 2 |
| java | 72/120 | **66** | 3 | 3 | 0 |

- **java は 66/72 が安全側**。生成コードは「1パスで補集合をハッシュに問い合わせる」形が定型で、
  `HashSet<Long> seen` に `target - val` を照会する実装が繰り返し現れる。
- **ts は 60/77 がタイムアウト**。同じモデルが同じ仕様文から二重ループを書く。
- **go はそもそも測れていない**（後述）。

## Go はビルドが通らず測定が成立しない

**go は 120世代中 101世代（84%）が build_fail。** 内訳（上位）:

| 件数 | エラー |
|---|---|
| 15 | `undefined: strconv` |
| 5 | `undefined: os` |
| 5 | `cannot use sc.Scan() (value of type bool) as string value in argument to strconv...` |
| 4 | `undefined: strings` |
| 4 | `multiple-value fmt.Sscanf(...) in single-value context` |
| 4 | `cannot use n (variable of type int64) as int value in assignment` |
| 3 | `expected 'package', found ``` |

**import 忘れ（`undefined: strconv` / `os` / `strings` で計24件）と標準ライブラリのシグネチャ誤りが主**で、
アルゴリズム選択以前の失敗である。**go の sec=0 は「危険な実装を書いた」ではなく
「実装が動かなかった」**と読むべきで、gemma4:e2b の go（build_fail 17/360）とは意味が違う。

## タイムアウトが本当に O(n²) 由来かの静的確認

生成コードを静的に走査し、ループ本体に別のループが含まれるか（＝入れ子ループ）を数えた
（`pipeline/detect_loops.py`、go/ts/java とも波括弧ブロックで判定）。

| lang | TIMEOUT 世代 | うち入れ子ループを検出 |
|---|---|---|
| go | 15 | **15 (100%)** |
| ts | 60 | **60 (100%)** |
| java | 3 | **3 (100%)** |

**78件すべてで入れ子ループを検出**。時間切れは推測ではなく実際に O(n²) を書いた結果である。

- **検出器の限界**: 「行を読む while の内側で split したトークンを回す」形も入れ子と数えてしまう。
  実際、java の合格66世代のうち25世代がこの形（`while (readLine) { for (part : parts) }`）で
  入れ子判定になっている。**入れ子検出だけでは危険と断定できない**ので、
  上の表は「TIMEOUT した世代の裏取り」としてのみ使うこと。

## func / sec 合格数（/10）

| shot | lang | 0.1 | 0.4 | 0.7 | 1.0 |
|---|---|---|---|---|---|
| zero | go | 0 / 0 | 1 / 0 | 0 / 0 | 0 / 0 |
| zero | ts | 2 / 0 | 3 / 0 | 1 / 0 | 0 / 0 |
| zero | java | 1 / 2 | 4 / 4 | 5 / 6 | 3 / 2 |
| one | go | 0 / 0 | 0 / 0 | 0 / 0 | 0 / 0 |
| one | ts | 1 / 0 | 8 / 0 | 7 / 0 | 7 / 1 |
| one | java | 0 / 0 | 5 / 5 | 6 / 6 | 6 / 6 |
| few | go | 8 / 0 | 1 / 0 | 0 / 0 | 0 / 0 |
| few | ts | 10 / 0 | 7 / 0 | 5 / 0 | 0 / 0 |
| few | java | 10 / 10 | 8 / 8 | 8 / 8 | 10 / 9 |

- **例示は go / ts の機能面を大きく押し上げる**（go few-shot temp0.1 で func 0 → 8、
  ts few-shot temp0.1 で 2 → 10）。**しかし sec は 0 のまま動かない。**
  例示が直すのはビルドエラーと出力書式であって、計算量ではない。
- gemma4:e2b で観測された「few-shot が java の func を壊す」現象は qwen では起きず、
  逆に java few-shot が最も安定している（10/10, 8/8, 8/8, 10/9）。
- 温度は sec に効かない。java で sec > 0 なのは温度によらず、ts / go で sec = 0 なのも温度によらない。

## gemma4:e2b との比較

| | gemma4:e2b | qwen3.5:4b |
|---|---|---|
| func | 324/360 (90%) | 127/360 (35%) |
| sec | **0/360** | 67/360 |
| ギャップ世代（func✓ sec✗） | 324 | 62 |
| ギャップ = 1.000 の条件 | **36/36** | 12/36 |
| 敵対的入力の TIMEOUT | 327 | 78 |
| 敵対的ケースの build_fail | 17 | **192** |

- **同じタスク・同じ閾値でも、モデルを替えるとギャップ率は 100% → 33% に落ちる。**
  差は「Java でハッシュ表を既定にするか」1点にほぼ集約される。
- **ただし qwen の低いギャップ率を「安全」と読んではいけない。** 分母の func が 35% しかなく、
  go では 84% がビルドすら通らない。**動くコードを書けないモデルは、危険なコードも書けない。**
  資源安全性の指標は、機能的な生成能力と切り離しては解釈できない。
