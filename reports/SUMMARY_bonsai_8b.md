# 圧縮 vs 特化：Bonsai-8B（1-bit）とミニコーダー仮説の答え合わせ（2タスク×36条件×k=10）

- **問い（[[mini-coder-hypothesis]] の残タスクより）**: qwen2.5-coder:1.5b は「特化で稼ぐ」側の
  ミニコーダー仮説（H1コスト／H2安全性）をどちらも棄却した。同じ~1GB級のメモリ予算を
  「**特化ではなく圧縮**」で使う選択肢——8.2B パラメータを丸ごと1-bit量子化した Bonsai-8B——
  なら func を維持できるか（H1')。低精度学習は資源安全な定石を伴うか（H2'）。
- **対象**: `bonsai-8b`（PrismML Bonsai-8B, Q1_0 1-bit, 1.16GB）を `cwe400_pair_sum` と
  `cwe401_memo_retain` の2タスクでスイープ。各タスク zero/one/few-shot × go/ts/java ×
  温度 {0.1, 0.4, 0.7, 1.0} の36条件360世代、計 **72条件720世代**。取得日 2026-09-09〜10、
  `docker_err` 0件。環境構築は `docs/bonsai_setup.md`。
- 個別総括: `SUMMARY_cwe400_pair_sum_bonsai_8b.md` / `SUMMARY_cwe401_memo_retain_bonsai_8b.md`
- ミニコーダー側の総括: `SUMMARY_mini_coder_1.5b.md`

## 結論

**H1'・H2' とも棄却。1-bit 圧縮は特化より悪い床になる。** 同じ ~1GB 級メモリで比べると、
Bonsai-8B は両タスクとも qwen2.5-coder:1.5b より func が低い。「特化で稼ぐ」も
「圧縮で稼ぐ」もこのメモリ予算では func を維持できず、**フルサイズモデル（gemma4:e2b /
qwen3.5:4b）から離れるほど func が崩れる**という単調な関係が4モデル目でも続いた。

## サイズ・量子化と func の関係（4点で見る単調性）

| model | 実効パラメータ規模 | ディスクサイズ | 精度 | cwe400 func | cwe401 func |
|---|---|---|---|---|---|
| gemma4:e2b | 2B級（汎用） | 7.2GB | 16bit系 | 90% | 50% |
| qwen3.5:4b | 4B級（汎用） | 3.4GB | 16bit系 | 35% | 27% |
| qwen2.5-coder:1.5b | 1.5B（コード特化） | 986MB | 16bit系 | 22% | 15% |
| **bonsai-8b** | **8.2B（1-bitネイティブ学習）** | **1.16GB** | **1bit** | **16.4%** | **5.0%** |

パラメータ数だけ見れば Bonsai-8B（8.2B）は qwen3.5:4b（4B）より大きいが、func は
qwen2.5-coder:1.5b（1.5B）よりさらに低い。**1-bit量子化がもたらす実効的な表現力の低下は、
パラメータ数を5倍以上積んでも「1.5Bを16bitで動かす」ことを下回る**——少なくとも
このコード生成タスクでは、量子化ビット数が実効性能を強く律速している。

## なぜそうなるか（定石・失敗様式の観察）

1. **go は3モデル中最も壊滅的**（cwe400: 0/120、cwe401: 0/120。coder:1.5b は3/120・79/120通過あり）。
   build_fail の内容も質的に違う：未使用 import・import 忘れに加え、
   **`import "container/map"` のように、Go の組み込み型 `map` を存在しないパッケージとして
   import する内部矛盾**（同じ関数内で `make(map[int]int)` は正しく書けている）が cwe401 の
   go だけで22件観測された。単なる知識不足ではなく、同一生成内で矛盾した知識を出力している。
2. **java は「構文が破綻したコードを繰り返す」という、他モデルにない失敗様式**を示す
   （`detect_loops.py` の `other` 分類が cwe400 java で67/120＝過半数、ループ構造の検出以前に
   コードが壊れている）。zero-shot・低温度で `Arrays.stream(scanner.lines())...` という
   同一パターンの構文エラーが複数条件にわたって再現した。
3. **cwe401 java の int32 桁溢れは coder:1.5b よりさらに悪化**（`long` 使用 10/120=8.3%、
   coder:1.5b は19/120=15.8%）。「保持しすぎ」以前の欠陥という構図は同じだが、より深刻。
4. **測定が成立する唯一の言語（ts）では、安全側と危険側の分岐点は他モデルと同じ**
   （クエリされた値だけをメモ化するか、経路上の全中間値を書くか）。ただし Bonsai-8B は
   **zero-shot でこの分岐に到達すらできない**（ts zero-shot 4温度すべて func=0、
   存在しない Node.js API `stream.ReadText` 等を幻覚）。例示に依存する度合いが他モデルより強い。

## コスト面（参考値）

| model | サイズ | cwe400 スイープ壁時計（36条件360世代） | cwe401 スイープ壁時計 |
|---|---|---|---|
| gemma4:e2b | 7.2GB | 5.6h | - |
| qwen3.5:4b | 3.4GB | 9.4h | - |
| qwen2.5-coder:1.5b | 986MB | 1.4h | - |
| **bonsai-8b** | **1.16GB** | **約2.1h** | **約6.1h** |

- 常駐メモリは coder:1.5b（986MB）とほぼ同級で軽いが、**壁時計は coder:1.5b より明確に遅い**
  （cwe400 で約1.5倍）。1-bit 量子化はディスク/メモリを圧縮しても、8.2B 相当の行列演算量は
  そのまま残るため、1.5B モデルより生成が遅い。「圧縮すれば速くなる」は成り立たない。
  cwe401 が cwe400 よりさらに遅いのは TIMEOUT ケース（10秒待ち×多数）の寄与が大きい
  （java の TIMEOUT だけで53件）。
- **8GBマシンでの常駐コストという点では coder:1.5b と同格**だが、速度面のメリットはない。

## 総合判定：ミニコーダー仮説（H1/H2）とその亜種（H1'/H2'）

| | H1(コスト): funcを保てるか | H2(安全性): 安全な定石を伴うか |
|---|---|---|
| 特化（qwen2.5-coder:1.5b） | 棄却（func 22%/15%、gemma4比で大幅減） | 棄却（java でもハッシュ表が既定にならない） |
| 圧縮（bonsai-8b） | **棄却（func 16.4%/5.0%、特化よりさらに悪い）** | **棄却（安全な定石はほぼ観測できない、func自体が壊滅）** |

**「小さく／安くしても func を保てるか」という問いに対して、特化・圧縮のどちらの経路も
このメモリ予算では答えは No だった。** 8GBマシンで実用的な選択肢は、現状の4モデルの中では
引き続き gemma4:e2b（7.2GB, func 90%/50%）が最有力で、コスト削減の余地は
このアプローチの延長線上にはなさそうである。
