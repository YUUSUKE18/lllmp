# CWE 横断考察 — ギャップの立ち方によるパターン分類

- **目的**: 個別タスクの総括（`SUMMARY_*.md`）を横に並べ、CWE 番号ではなく
  「セキュリティギャップがどう立つか」でタスクを分類し、横断的なパターンを整理する。

  手段指定の2アーム実験（CWE-1333 × 2モデル）。

## 結論（先に要旨）

**セキュリティギャップの有無は CWE 番号と対応しない。** 決めているのは次の2軸である:

1. **そのタスク×モデル×言語で、モデルの既定の書き方（定石）が安全側か危険側か**（パターン①②③）
2. **その欠陥が測定・実行環境に映るか**（パターン④）

同じ CWE-400 がギャップ 0（`cwe400_unique`）にも全滅（`cwe400_pair_sum`）にもなり、
同じ CWE-770 が空振り（`cwe770_rle_expand`）にも 720世代 sec 合格ゼロ（`cwe770_stream_max`）にもなることが、
CWE 番号が予測変数にならないことの最も簡潔な証拠である。

また横断的に、**「機能的に正しく書ける能力」と「資源安全に書ける能力」は独立**であり、
モデル改良・例示・温度・注意喚起といった介入はすべて前者しか動かさない（後述）。

## 4つの構造パターン

| パターン | タスク (CWE) | ギャップ | 決め手 |
|---|---|---|---|
| ① 既定が安全で罠が空振り | `cwe400_unique`(400・TS/Java)、`cwe770_rle_expand`(770) | 0 | 定石が最初から安全側（map/set・算術） |
| ② 既定が危険で全滅 | `cwe400_pair_sum`(400)、`cwe770_stream_max`(770) | ほぼ 1.000 | 定石が危険側（二重ループ・全読み込み） |
| ③ 定石そのものが罠（中頻度） | `cwe401_memo_retain`(401) | 10〜12% | 教科書的な再帰メモ化が仕様の要求と一致して発現 |
| ④ sec 判定に映らない | `cwe1333`(ReDoS)、`cwe835`(無限ループ) | 見かけ上ほぼ 0 | 実行エンジンや欠陥の現れ方が測定の想定とずれる |

### ①② ギャップの有無は「モデルの既定」が決める

較正上、どのタスクでも罠は実在する（naive 実装は確実に落ちることを
`docs/*_calibration.md` で担保している）。にもかかわらず:

| タスク | 安全な解法 | モデル（gemma4:e2b）の既定 | 観測されたギャップ |
|---|---|---|---|
| `cwe400_unique` | map/set で O(n) | **map/set**（安全側） | TS/Java で 0 |
| `cwe770_rle_expand` | 算術で定数メモリ | **算術**（安全側） | 全36条件で 0 |
| `cwe400_pair_sum` | ハッシュ表で O(n) | **二重ループ**（危険側） | **全36条件で 1.000** |
| `cwe770_stream_max` | ストリーム処理 | **全読み込み**（危険側） | 全36条件で 1.000（2モデル・720世代 sec 合格 0） |

**「人間が素朴に書きそうな危険な実装」を基準にタスクを設計してもギャップは立たない。**
立つのは「モデルが実際に書く実装」が危険なときだけである。

さらにこの既定は**モデル固有ですらなく、モデル×言語の組で決まる**。
`cwe400_pair_sum` で gemma4:e2b は全360世代が二重ループを選んだのに対し、
qwen3.5:4b は **Java でだけ**ハッシュ表（`HashSet<Long>` に補集合を照会する1パス）を既定にし、
ビルドが通った Java 72世代のうち 66 が安全側だった。同じ qwen が TS では二重ループを書く
（TIMEOUT 60/77）。ゆえにギャップ = 1.000 の条件は gemma 36/36 に対し qwen 12/36（ts 9 / go 3 / java 0）。

**ただしこの「安全さ」はタスクをまたいで一般化しない。** 同じ qwen が CWE-401 では
gemma と同様に再帰メモ化（危険側の定石）を選び、メモリ由来ギャップ率は
gemma 10.3% に対し qwen 11.9% とほぼ同等だった。pair_sum の Java の安全性は
「ハッシュ表という別の定石がたまたま既定だった」ことに由来する局所的な性質である。

### ③ CWE-401 は「定石＝罠」型 — 発現率が測定方法を選ぶ

`cwe401_memo_retain` のギャップ世代は、`pipeline/memo_style.py` の分類で
**gemma 31/37 (84%)、qwen 41/43 (95%) が再帰メモ化**。各再帰フレームが `memo.put` を呼ぶことで
経路上の中間値（10万クエリで814万件）が暗黙に全部保持される形であり、
**危険なコードを書こうとした結果ではなく、教科書どおりに書いた結果**という点で②と同類である。

②と違うのは発現率で、世代単位 10〜12% にとどまる。このため:

- **条件単位の pass@10 ギャップでは 36条件中 2条件しか立たない**（gemma）。
  世代単位では 37件あるのに、指標の粒度で存在がほぼ消える。
- CWE-835 の「宣言値を信じて sec だけ落ちた」14件も同様に、条件単位では 35/36 条件でギャップ 0。

**高頻度型（②）は pass@10 で見えるが、中低頻度型（③④）は世代単位で数えないと見落とす。**
どの指標が妥当かはパターンに依存する、という方法論上の含意が出ている。

### ④ 測定に映らない2つの機序

**CWE-1333（ReDoS）— 実行エンジンが観測可能性を決める。**
危険な正規表現を書く率自体は使用世代の 1〜3% ある（アームB 合計 7/299 = 2.3%）。
しかし sec（実測）に現れたのは ts の 3件だけで、**go（RE2）と java（JDK 21）は
同じ危険パターンを線形時間で処理するため、そのまま合格する**。
脆弱性が「コード」ではなく「コード×実行エンジン」の性質である例で、
静的分類（`pipeline/analyze_regex.py`）を併用しなければ「安全に書けた」と誤読するところだった。
**3言語の sec を平均する操作はこのタスクでは無効**である。

**CWE-835（無限ループ）— 罠の設計形とモデルの誤り方がずれる。**
狙った無限ループ（TIMEOUT）は gemma 360世代で 0件、qwen でも1件のみ
（しかもその1件は機能ケースでも落ちるためギャップにならない）。
しかし「宣言値を信じる」根本欠陥そのものは gemma 29世代・qwen 65世代で観測され、
**反復回数ではなく出力値（`count=2147483647 sum=15` の転記）として現れた**。
資源判定だけなら無傷に見えるが、敵対的入力に対する出力照合が判定に入っていたため捕捉できた。
**罠は「設計した形」ではなく「モデルの誤り方」で現れる**ので、可用性タスクでも出力照合は必須である。

## 横断パターン1: 症状は言語が決め、モデルは build_fail 率しか動かさない

CWE-770 / CWE-401 で一貫して、**ビルドが通った世代の敵対的入力での症状は言語でほぼ決定する**:

| lang | 症状 | 機序 |
|---|---|---|
| go | **無言の空出力（exit=0）** または rss 超過 | `bufio.Scanner` の既定トークン上限 64KB を超える1行を読めず、無出力のまま正常終了 |
| ts | crash（exit=134） | V8 ヒープ枯渇（`readFileSync` → `split` で数百MB） |
| java | crash（exit=1） | `OutOfMemoryError`（コンテナの OOM killer には届かない） |

CWE-770 では go でビルドが通った世代の **100% が wrong_answer**（gemma 93/93、qwen 22/22、
全件 `bufio.NewScanner` を `Buffer()` 拡張なしで使用）、java の 100% が crash（gemma 120/120、qwen 69/69）。
**モデルを替えると build_fail の比率だけが動き、その先の症状分布は動かない。**

運用上は **go が最も危険**である。ts/java は「落ちる」ことで異常を知らせるのに対し、
go は巨大入力を黙って捨てて終了コード 0 を返し、呼び出し側からは成功に見える。
1.3MB（CWE-400）でも 34MB（CWE-770）でも同一機序なので、入力規模の問題ではなく言語定石の構造的欠陥である。
（旧判定がこの無言失敗を「安全」と数えて「Go だけギャップ 0」と誤結論した経緯は
`SUMMARY_cwe770_shots.md` の「修正した2つの判定の穴」を参照。）

なお qwen3.5:4b は go の build_fail が 84%（pair_sum 101/120、memo_retain 95/120）に達し、
**go についてはそもそも測定が成立していない**。「動くコードを書けないモデルは危険なコードも書けない」ので、
低いギャップ数を安全性と読んではならない。

## 横断パターン2: 介入は func にしか効かず、sec を動かさない

| 介入 | func への効果 | sec への効果 |
|---|---|---|
| shot 数（zero→one→few） | 大きく動く（qwen で +、gemma java few-shot で −もある） | **ほぼゼロ**（192条件+48条件で safe×java×few の3条件のみ、しかも func 10→3 に崩壊） |
| 例示の資源安全性（safe/unsafe） | 大きく動き、符号が読めない | safe 例示 24条件中21条件で sec=0 のまま |
| 温度（0.1〜1.0） | qwen で強く効く | 効かない |
| モデル交代（gemma→qwen） | 大きく動く（CWE-770: func 318→104） | **動かない**（sec 0→0） |
| 手段指定（「正規表現を用いよ」） | — | **危険を約4倍**、2モデルで再現（p=0.00046 / 0.0012）。主因は使用率の増加（go 0%→78%、java 18%→71%） |
| 目標指定（「安全に書け」1文） | タスク×モデルで**向きが反転**（pair_sum gemma −16pt / memo_retain gemma +12pt / qwen 両方不変） | 効くのは qwen×pair_sum×ts の 1.3%→20.0% のみ。**副作用の build_fail 増加だけがモデル横断で共通** |

- **例示は安全性を与えないどころか、脆弱性の供給源になりうる。** CWE-400/770 の go では、
  例示が教える `bufio.Scanner` がまさに 64KB 制限を持つ書き方であり、例示が脆弱性の原因そのものだった。
- **目標を述べる注意喚起が効くのは「安全な代替が明確に存在し、かつモデルが未採用」の狭い条件だけ**
  （qwen×pair_sum×ts）。既に安全が既定なら天井効果で効かず（qwen×pair_sum×java 91.7%）、
  **危険が仕様の要求（「メモ化せよ」）に埋め込まれていると無力**（memo_retain 両モデル）。
- したがって実務的には、仕様に手段を書くことは**その手段固有の失敗様式ごと引き受ける**ことであり、
  「安全に書いて」と添えることは**対策として当てにできない**。

## 横断パターン3: 脆弱性の有無を決めるのは書き方ではなく入力規模のことがある

CWE-400 `unique`（1.3MB）と CWE-770 `stream_max`（34MB）は、TS/Java でほぼ同じ
「全体を読んでから処理する」実装が生成される。前者では資源に余裕があり全条件 10/10、
後者では全滅。**同じ実装が入力規模だけで安全にも危険にもなる**。
タスク設計側から見れば、敵対的入力の規模設定が「CWE が成立するか」を決めている。

## 測定設計への教訓（本プロジェクトで実際に踏んだ穴）

1. **資源だけ見る可用性判定は不十分。** 異常終了（JVM の exit=1）と、敵対的入力に対する
   出力の正しさ（go の無言空出力、CWE-835 の宣言値転記）を照合しないと、系統的に見逃す。
2. **条件単位の pass@10 ギャップは発現率 10% 程度の欠陥を捉えられない**（CWE-401/835）。
   世代単位で数えること。
3. **sec 単独は安全性の指標にならない。** sec > func の条件が複数あり（CWE-401 qwen 等）、
   「危険な最適化を書けなかった」ことがたまたま資源安全側に出るだけの世代を含む。
4. **ギャップの生カウントをアーム間・モデル間で直接比べてはいけない。** 分母（func 通過数）が
   動くため交絡する（memo_retain hint: 37→62 は見かけ上の悪化、func 統制後 p=0.081）。
5. **実測に映らない欠陥は静的分類で補う**（CWE-1333 の `analyze_regex.py`、
   pair_sum の `detect_loops.py`、CWE-401 の `memo_style.py`）。逆に静的検出だけでも誤るので
   （入れ子量化子の静的判定で2度誤検出）、実測との突き合わせが要る。

## 追記（2026-09-07）: 定石は同系列にも継承されない

`qwen2.5-coder:1.5b` を2タスクで追加測定した（`SUMMARY_mini_coder_1.5b.md`）。
「タスク×モデル×言語」という粒度の主張を、**モデル軸の内側でさらに1段細かく**する結果になった。

- `cwe400_pair_sum` の java で安全側の定石（ハッシュ表）を持つのは qwen3.5:4b だが、
  **同じ Qwen 系列のコーディング特化 1.5B は二重ループが既定**（120世代中 80世代、ハッシュ 5件）。
  安全な定石は系列やベンダではなく、**そのモデル個体の性質**である。
- **コード特化の事前学習は資源安全な定石を伴わない。** func 通過を分母にした条件付きギャップ率は
  CWE-400 で 0.949、CWE-401 で 0.778 と、汎用 2B/4B より悪い（Holm 補正後も有意）。
- パターン②（既定が危険で全滅）は、モデルを小さく特化させても解消されない。
  一方でパターン④（測定に映らない）が拡大する: go は build_fail 79〜97/120、
  java は CWE-401 で int32 桁溢れにより func 1/120 と、**そもそも測れない条件が増える**。
  **「func が低いモデルは sec も測れない」**ことは、モデル比較の下限を決める実務的な制約である。

## まとめ

- CWE 番号はギャップの予測変数にならない。予測に必要な粒度は **タスク×モデル×言語**。
- ギャップが立つ条件は「モデルの定石が危険側」であること。定石が安全なら罠は空振りし（①）、
  危険なら例示・温度・注意喚起のどれでも救えない（②③）。
- 測定に映らない欠陥（④）が確実に存在するため、資源実測・出力照合・静的分類の3点セットが要る。
- func と sec は独立の能力であり、観測したすべての介入は func しか動かさなかった。
  **「機能的に正しく書けるようになること」は「資源安全に書けるようになること」を含意しない。**
