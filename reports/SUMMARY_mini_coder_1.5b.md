# ミニコーダーモデル仮説の検証（qwen2.5-coder:1.5b, 2タスク×36条件×k=10）

- **仮説（2026-09-06、ゼミでの提案）**: 汎用 4B 級の代わりに**小さいコーディング特化モデル**を使えば、
  導入コスト（メモリ・時間）を抑えつつ機能面（func）を維持できるのではないか。
  さらに、プロンプト介入では sec が動かないことが分かっている以上、
  **学習介入（LoRA）で「育てる」余地があるのは特化モデルの側ではないか**。
  - **H1（コスト）**: 1.5B 特化モデルは 2B/4B 汎用モデルの func を保てる。
  - **H2（安全性）**: コード特化の事前学習は、資源安全な定石（ハッシュ表・有界キャッシュ）を伴う。
- **対象**: `qwen2.5-coder:1.5b`（986MB）を `cwe400_pair_sum` と `cwe401_memo_retain` の
  2タスクでスイープ。各タスク zero/one/few-shot × go/ts/java × 温度 {0.1, 0.4, 0.7, 1.0} の
  36条件360世代、計 **72条件720世代**。取得日 2026-09-06、`docker_err` 0件。
- 個別総括: `SUMMARY_cwe400_pair_sum_qwen2.5_coder_1.5b.md` /
  `SUMMARY_cwe401_memo_retain_qwen2.5_coder_1.5b.md`

## 結論

**H1・H2 とも棄却される。** coder:1.5b は func を維持できず、
かつ **func 通過を分母にした条件付きギャップ率は両タスクとも他の2モデルより悪い**。
「特化させれば安全になる」も「小さくしても機能は保てる」も成り立たなかった。

安くはなった（スイープ壁時計は gemma4:e2b の約 1/4、常駐メモリは 986MB 対 7.2GB）が、
**安さの正体は「動くコードを書けないこと」**である。

比較は「func 通過世代のうちギャップになった割合」の 2×2。

| 比較 | 割合 | p | Holm 補正後 |
|---|---|---|---|
| CWE-401: coder:1.5b vs gemma4:e2b | 0.778 vs 0.207 | 3.2×10⁻¹⁴ | **1.3×10⁻¹³** |
| CWE-400: coder:1.5b vs qwen3.5:4b | 0.949 vs 0.488 | 3.8×10⁻¹³ | **1.2×10⁻¹²** |
| CWE-400: coder:1.5b vs gemma4:e2b | 0.949 vs 1.000 | 0.0014 | **0.0028** |
| CWE-401: coder:1.5b vs qwen3.5:4b | 0.778 vs 0.619 | 0.048 | **0.048** |

- **4比較すべてが補正後も有意**。ただし CWE-400 の対 gemma4:e2b だけは coder が「わずかに良い」向き
  （0.949 < 1.000）で、これは gemma4 が 324/324 と天井に張り付いているため。
  **実質的には「gemma4 と同じく全滅、qwen3.5:4b より明確に悪い」**と読むのが正しい。
- 補正は `docs/slides.md` と同じ Holm 法。

## なぜそうなるか（定石の観察）

1. **Java のハッシュ既定は同系列に継承されない。** `cwe400_pair_sum` の生成コード静的分類では、
   qwen3.5:4b の java は 120世代中 112世代がハッシュ表を使い二重ループは3件だけなのに対し、
   **coder:1.5b の java は 80/120 が素の二重ループ**（ハッシュ 5件）。
   「安全側の定石を持つのは Qwen 系列だから」ではなく、**そのモデル固有の性質**である。
2. **`cwe401_memo_retain` の java は int32 で軌道を持つ**（120世代中 101世代が `long` を使わない）ため、
   機能ケースの時点で落ちて測定にならない（func 1/120）。
3. **go は3モデルとも測定が成立しない**（coder:1.5b の build_fail は cwe400 で 79/120、cwe401 で 97/120）。
   未使用 import と import 忘れという、アルゴリズム以前の失敗。
4. **測れた ts では、狙った欠陥がそのまま出る**。cwe401 の ts はヒープ枯渇の abort（`exit=134`）が46件、
   ギャップ世代42件中34件が「経路上の中間値をすべてメモ化する」再帰実装だった。

## コスト面（参考値）

| model | サイズ | cwe400 スイープ壁時計（36条件360世代） |
|---|---|---|
| gemma4:e2b | 7.2GB | 5.6h |
| qwen3.5:4b | 3.4GB | 9.4h |
| **qwen2.5-coder:1.5b** | **986MB** | **1.4h** |

- **壁時計には Docker での動的テスト時間が含まれる**（TIMEOUT ケースは1件10秒）ので、
  純粋な生成速度の比較ではない。TIMEOUT が最も多い gemma4:e2b は不利側に、
  ビルドすら通らない世代が多い coder:1.5b は有利側に振れる。
- それでも **8GB マシンで 986MB は常駐コストとして決定的に軽い**（gemma4:e2b の 7.2GB はほぼ限界）。
  H1 が棄却されたのは速度・メモリではなく **func の維持**の一点である。

## 次にやること

- **coder:3b アーム**: 1.5B → 3B で func が戻るなら、H1 は「サイズの問題」に還元できる。
  戻らないなら特化系列そのものの性質。
- **LoRA fine-tune アーム（H2 の本命）**: プロンプト介入が sec を動かさないことは
  `ANALYSIS_cwe_patterns.md` で確立済み。**学習介入がフロンティアを動かすか**が残る問い。
  ただし本結果より、**func が 15〜22% の土台で sec を測ると分母が薄すぎる**。
  fine-tune は func の回復とセットで評価する必要がある。
- **Bonsai-8B アーム**: 1-bit 量子化で coder:1.5b と同メモリ級。
  「圧縮で稼ぐ vs 特化で稼ぐ」の同コスト対決。まず同一スモーク
  （`pair_sum` × java × zero-shot × temp0.1）で床を越えるか確認してから2タスクスイープ。
