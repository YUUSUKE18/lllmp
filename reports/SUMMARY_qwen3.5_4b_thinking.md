## ts では thinking が壊す: 標準入力の読み方が非ブロッキング API に切り替わる

ts の崩壊は単一の原因に還元できる。**thinking を有効にすると、qwen は動いていた
ブロッキング読み込みを捨てて非ブロッキングの Stream API に乗り換える。**

生成コード 100 世代ずつを静的に数えた、標準入力の読み方の分布:

| 読み方 | qwen OFF | qwen **ON** | gemma OFF | gemma ON |
|---|---|---|---|---|
| `readFileSync(0, …)`（ブロッキング・正しい） | **63** | 0 | **98** | 76 |
| `process.stdin.read()`（非ブロッキング・null が返る） | 12 | **77** | 0 | 0 |
| `process.stdin.readSync`（その型に存在しない） | 0 | 0 | 0 | 22 |
| `readline.createInterface` | 17 | 2 | 2 | 2 |
| `for await (const … of process.stdin)` | 0 | 4 | 0 | 0 |
| `process.stdin.on(…)` | 2 | 2 | 0 | 2 |

`process.stdin.read()` は Readable ストリームのバッファにデータが溜まっていなければ
`null` を返す。プロセス起動直後に同期的に呼べば、ほぼ必ず `null` である。
qwen の think ON はこれを 77/100 世代で選び、さらに **`null` ガードを
トップレベルの `return` で書く**ため、2 通りの壊れ方が出る:

```ts
const input = process.stdin.read();   // ← ほぼ必ず null
if (!input) {
  console.log('valid=0');
  return;                             // ← トップレベル return は TS1108
}
```

世代単位の内訳（各 100 世代）:

| 結果 | qwen ON | qwen OFF | gemma ON |
|---|---|---|---|
| func 合格 | 5 | **32** | **68** |
| `TS1108` トップレベル `return` でビルド不成立 | **31** | **0** | 0 |
| 入力を読めず `count=0` / 空を出力（誤答） | 21 | 2 | 0 |
| 実行時エラー（exit=1） | 13 | 9 | 2 |
| 空応答（thinking 予算切れ） | 10 | 0 | 0 |
| `TS2365` 型混在（number と bigint） | 9 | 11 | 1 |
| `TS2339` プロパティが存在しない（gemma の 19 件は全件 `readSync` 由来） | 0 | 3 | **19** |
| その他ビルドエラー | 8 | 23 | 4 |
| その他の誤答 | 3 | 20 | 6 |

- **`TS1108` は think OFF では 0/100、think ON では 31/100**（p=5.9×10⁻¹¹）。thinking が持ち込む
  エラー class であり、モデルの ts 能力の不足ではない。
- 残る 21 世代は構文的には通るが、`null` を読んで **`count=0` を黙って出力**する。
  可用性テストからは「誤答」として見え、**ビルドエラーより検知しにくい**。
- つまり **1 つの API 選択（`readFileSync(0)` → `process.stdin.read()`）が
  ts の失敗 52/100 を説明する**。

これは cwe400_pair_sum で「think OFF は 20/20 が二重ループ、think ON は 20/20 がハッシュ表」
という既知の現象と同じ型である。**thinking は既定イディオムを入れ替える。入れ替え先が
安全側なら func-sec は跳ね上がり（pair_sum）、壊れた API なら全滅する（ts の stdin）。**

gemma も同じ方向にずれるが程度が浅い。`readFileSync(0)` を 76/100 で保ち、
ずれた 22 世代が `process.stdin.readSync`（その型に存在しないメソッド）を使い、
**うち 19 世代が `TS2339` でビルド不成立**になる（残り 3 世代は実際には通らない分岐に書かれていた）。
**ts で thinking が安全性を上げないのは両モデル共通だが、qwen は乗り換え先が
「型は通るが実行時に何も読めない」API なので誤答として沈み、gemma は
「型検査で落ちる」API なのでビルド段階で露見する。**

## 「正しく書けるほど踏む」2 例

### cwe401_memo_retain: 実装に失敗していたから安全だった

think OFF の「安全な」世代は、**メモ化の実装に失敗していたから安全だった**。
java temp0.1 の think OFF 10 世代のうち 9 世代が `memo` を読むだけで `memo.put` を
一度も呼ばず、メモ化テーブルが空のまま動いていた。メモリが増えないので可用性ケースを通る。

think ON は教科書どおりの再帰＋メモ化を書く（`memo.put` あり）。これは CWE-401 が
罰するべき実装そのもので、10 万個の異なる入力に対し中間値を無制限に保持してクラッシュする。

### cwe770_stream_max: go は 10/10 が入力を丸ごとバッファする

think ON の go は func 6/10・sec 0/10。**10 世代すべてが `io.ReadAll(os.Stdin)` で標準入力を
全部読み、さらに `strings.Split` で全要素のスライスを作る**。機能ケース（小入力）は通り、
大きなストリームで RSS 125〜248MB（上限 102MB）に達して落ちる。残り 4 世代の func 失敗は
`val > maxVal (mismatched types int64 and int)` の型エラーで、メモリとは無関係。

同じタスクの java ON は 8/10 が `Scanner` でトークン単位に読み進め、うち 7 世代が sec 合格。
**同じモデル・同じプロンプト・同じ thinking 設定でも、言語ごとに手が伸びる既定イディオム
（go の `io.ReadAll`+`Split` 対 java の `Scanner`）がそのまま安全性の差になる。**

## func-sec 指標の解釈に穴がある

**データセット全体の監査**（`pipeline/memo_audit.py`。`func-sec` を通った cwe401 世代のうち、
メモ化への書き込みが 0 の割合）:

| モデル | 言語 | func-sec | うち書込 0 | 割合 |
|---|---|---|---|---|
| qwen3.5:4b | java | 21 | 10 | **48%** |
| qwen2.5-coder:1.5b | ts | 11 | 6 | **55%** |
| qwen3.5:4b（ヒント有） | java | 19 | 6 | 32% |
| gemma4:e2b | go / java / ts | 45 / 42 / 55 | 0 / 0 / 0 | **0%** |
| bonsai-8b | ts | 8 | 0 | 0% |

gemma4:e2b は 142 件すべてが正しくメモ化した上で安全（上限を設ける等）。
**qwen 系だけが「実装に失敗した結果として安全」を多く含む。**

→ **func-sec は「正しく実装した上で安全」と「実装に失敗して安全」を区別できない。**
メモ化が本質のタスクでは、安全判定に実装が機能しているかの確認を併せる必要がある
（本監査は `put`/`set`/添字代入の有無で静的に判定）。

## 結論

1. **既存スイープの `think=false` は qwen3.5:4b の func を go で強く過小評価し、
   ts では過大評価していた**（go 1/100→58/100、ts 32/100→5/100）。
   論文で qwen の数値を示す際は「thinking 無効時の値」と明記する必要がある。
2. **安全性（func-sec）は全体では改善するが（22%→34%, p=0.002）、言語で向きが逆になる。**
   go +37、java +22 に対し **ts は −24 ポイント**。
   「thinking を有効にすれば安全になる」は言語をまたいで成り立たない。
3. **thinking が壊す経路は 2 つある。**
   - **「仕様を正しく満たす」能力だけが上がり、仕様に書かれていない資源制約は考慮しない**。
     そのため資源制約が正しい実装と衝突するタスク（cwe401_memo_retain、
     cwe770_stream_max の go/ts）では、正しく書けるモデルほど脆弱性を踏む。
   - **既定イディオムそのものを入れ替える**。入れ替え先が安全なら跳ね上がり（cwe400_pair_sum:
     二重ループ → ハッシュ表）、壊れた API なら全滅する（ts: `readFileSync(0)` →
     `process.stdin.read()`）。**どちらに転ぶかは事前に予測できない**ので、
     推論設定を変えたら測り直すしかない。
4. **func-sec 指標そのものに解釈上の穴がある**。qwen 系では安全判定の 3〜5 割が
   「実装の失敗による副作用」だった。gemma4:e2b にはこの問題がない。
5. **同一 30 条件で比べると gemma4:e2b が think ON/OFF どちらでも有意に上**
   （ON 180/300 対 102/300, p=2.4×10⁻¹⁰）。推論設定を揃えてもモデル順位は入れ替わらない。

## 限界

- **zero-shot のみ。one/few-shot は未取得**。temp0.7 は cwe400_pair_sum / cwe401_memo_retain の
  2 タスクのみで、他の 6 タスクは temp0.1 の 1 点しかない。
  ts の崩壊が温度でどう動くかは pair_sum（0/10 → temp0.7 で 2/10）しか手がかりがない。
- ts の失敗は `process.stdin.read()` という **1 つの API 選択に 52/100 が集中**している。
  プロンプトで読み方を指定すれば消える可能性が高く、**「qwen は ts が弱い」ではなく
  「qwen の thinking はこの API を選ぶ」が正確な記述**。プロンプト側の対処は未検証。
- `num_ctx=16384` 固定。空応答 26/300 は ON 側だけの不利で、さらに広げれば減る可能性がある。
  ただし空応答を全部除いても結論（とくに ts の悪化）は変わらない。
- 取得時期: ON 側は 09-16〜19（go/java）と 09-24〜26（ts・cwe400_unique）、OFF 側は 08-19〜09-01。判定コードは 08-30 以降不変で、
  bonsai 検証時の rejudge（504 世代）でも差分 0 を確認済み。唯一 08-30 より前なのは
  cwe770_stream_max の OFF（08-19）だが、この条件の失敗は 20 世代すべてが
  build_fail か実行時クラッシュで、閾値判定に依存しないため比較は成立する
  （Docker 復帰後に `pipeline/rejudge.py` で確認するのが望ましい）。
